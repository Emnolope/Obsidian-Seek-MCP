# Context Summary: Integrating PicoClaw with Obsidian Embedding Vectors

## Executive summary

This document is a research and design note about connecting PicoClaw to an Obsidian personal knowledge base using semantic retrieval rather than a full-text-only search. The core idea is to use the embeddings already generated by an Obsidian plugin (initially discussed as Similar Notes, later clarified as the Seek plugin stack) and feed those vectors into an MCP-compatible retrieval layer that PicoClaw can use for RAG-style question answering.

The author wants PicoClaw to search a vault containing thousands of Markdown notes, find the most relevant notes by semantic similarity, and then use those notes as context for its reasoning. The desired pattern is:

- Obsidian generates embeddings for notes
- a local vector/index store is preserved in a durable format
- PicoClaw or an MCP server reads that index
- cosine similarity / nearest-neighbor search selects the top-k relevant notes
- those notes are then injected into the agent context

This is not a simple keyword search problem; it is an architecture problem about local data access, Git sync, plugin compatibility, and the difference between human-facing Obsidian plugins and machine-facing MCP tools.

## The original problem statement

The author runs PicoClaw on a phone (initially a OnePlus 6T/Android environment), and wants it to search a vault of roughly 5,000 Markdown notes in Obsidian. The vault uses the Similar Notes plugin, which computes embedding vectors for notes. The goal is to avoid making PicoClaw generate its own embeddings from scratch.

The stated requirements are:

- search across an Obsidian vault of thousands of notes
- compare note embeddings using cosine similarity or KNN-style retrieval
- retrieve the most relevant notes for a task or query
- use the results as retrieval-augmented context for PicoClaw
- reuse existing embeddings instead of duplicating compute work

## Key technical insight

The central design principle is: if a plugin is already creating embeddings for the vault, the agent should not recompute them unless necessary.

This avoids:

- duplicate embedding cost
- duplicated storage and indexing infrastructure
- inconsistent retrieval quality between the human tool and the AI tool

The intended architecture is a shared read-side semantic index that both the Obsidian workflow and the AI workflow can use.

## Important findings and corrections

### Similar Notes / local storage issue

An early version of the discussion emphasized that Similar Notes stores its vector index in IndexedDB, which is local to the Obsidian app instance and not easily portable. That matters because:

- IndexedDB is device-specific
- it is not a git-friendly vault file
- it is not typically accessible as a plain data file that a separate process can read easily
- the plugin mainly exposes note-to-note similarity exports, not a full vault-wide vector export

This is one of the biggest practical constraints: the plugin is excellent for in-Obsidian semantic browsing, but not necessarily a clean interface for an external agent to query from Termux or a Codespace.

### The “two vaults” topology

The author later clarifies an important operational constraint: the Obsidian vault used by the AI is not the same live working vault. Instead, there are two local vault copies on the phone, synced via Git, so that the agent cannot directly mutate the human’s source-of-truth notes.

This architecture is designed for safety:

- human notes stay authoritative
- the agent works from a copy or a mirrored vault
- changes are synced via Git rather than through live editing in the user’s active vault

### The Seek plugin becomes the practical focus

The document eventually pivots from Similar Notes to the Seek plugin, which appears to be a more relevant option for a Git-friendly, on-disk semantic index. Seek is described as open source and usable in a repo-based workflow where the generated files live within the vault repo itself.

This matters because it creates a real path for an MCP server to read actual on-disk stored semantic data rather than trying to scrape browser-local IndexedDB.

## The real design tension

The document is ultimately about a tradeoff between two constraints:

- Human side: Obsidian on mobile is restrictive and plugin runtime capabilities are limited
- Agent side: Termux / Codespaces / local Linux tooling is more flexible and can run Python, Go, MCP servers, and CLI tools

This means the key decision is not “which MCP server is best?” but “what format does the human-facing plugin actually store, and can the agent read that same format reliably?”

## Desired solution architecture

The desired architecture is a two-part system:

1. Obsidian plugin side
   - stores embeddings or semantic indices for the vault
   - is compatible with the human workflow and phone/mobile constraints

2. Agent / MCP side
   - reads the same semantic index
   - exposes tools such as search, nearest-neighbor retrieval, note fetch, and context extraction
   - serves PicoClaw or another AI agent

The plugin and MCP server are separate components but should share the same underlying data model rather than each computing their own embeddings independently.

## Search strategy and evaluation criteria

The document repeatedly emphasizes a methodical process rather than jumping to a solution:

- list the hard constraints first
- classify the plugin by storage type
- determine whether storage is portable, git-friendly, and mobile-safe
- find out whether the data is in IndexedDB, SQLite, JSON, or a custom format
- then decide whether an MCP wrapper is feasible

The key evaluation dimensions are:

- mobile compatibility
- local-first operation
- no forced cloud dependency
- portable on-disk storage
- git compatibility
- ability to expose semantic search via MCP
- ability to share data between human and agent workflows

## Practical conclusion

The document concludes that the most viable architecture is not “plug an Obsidian plugin directly into PicoClaw” but rather:

- use a plugin that stores semantic data in a real, readable local database or index file
- build a local MCP server around that data source
- let PicoClaw interact with the MCP server for similarity search and retrieval

The core lesson is that a plugin’s storage format decides whether it can become part of an external AI pipeline. IndexedDB and browser-local stores are convenient for Obsidian but awkward for AI tooling; real files or SQLite-like on-disk indexes are much easier to integrate.

## Final takeaway

This file is essentially a design memo for a local semantic retrieval pipeline connecting Obsidian and PicoClaw. It is not just about embeddings; it is about selecting the right plugin, understanding the data substrate, and building an MCP bridge that can work with the same vault data without creating duplicate indexing pipelines or damaging the human’s source notes.

The overall direction is clear:

- use Obsidian’s semantic plugin to generate embeddings
- prefer on-disk, git-friendly, mobile-compatible storage
- expose retrieval via a local MCP server
- let PicoClaw consume those results as context rather than trying to bootstrap a separate embedding system

## Conversation handoff: clarified architecture and implementation direction

### Why this repository exists

The goal is to build an MCP server that lets PicoClaw retrieve relevant context from an Obsidian vault using semantic embeddings that Seek has already generated.

The motivating constraint is compute and duplication. The vault contains thousands of Markdown notes. Re-embedding the same vault in a second application would repeat expensive work, create a second index, and potentially produce different retrieval results. Seek already performs the embedding work inside Obsidian, so the MCP integration should reuse Seek's results.

The operational setup uses two vault copies on the phone:

- the human vault is the source of truth
- the agent works from a separate copy
- Git synchronizes the copies
- the agent must not directly mutate the human's active notes

The desired MCP surface is read-only semantic retrieval first. Note mutation, Git operations, and reindexing are out of scope until retrieval is reliable.

### Important conceptual correction: IndexedDB is private application storage

Seek does not avoid copying data. During indexing, it copies/indexes note content, chunk metadata, file mappings, and embedding tiers into its own IndexedDB stores.

Seek can use those stores because it runs inside Obsidian's plugin runtime. A separate process such as an external MCP server, PicoClaw, or a Termux process cannot normally open the same IndexedDB database as an ordinary filesystem database.

The practical boundary is:

```text
Markdown note
   -> Seek chunks and embeds it
   -> Seek stores chunks, mappings, and vector tiers in IndexedDB
   -> Seek searches IndexedDB from inside Obsidian
```

IndexedDB is not necessarily secret or cryptographically protected. It is app/runtime-local storage. The problem is access and ownership, not that the information is intrinsically inaccessible.

An Obsidian plugin running in the same runtime may be able to open Seek's IndexedDB database if it knows the database name and schema. That would be a private implementation coupling, not a stable public API. A schema migration or database-name change could break it.

### What the current Seek sidecar contains

The generated directory was inspected at:

```text
/workspaces/system-vault/Seek Index/
```

It contains:

```text
meta.mobile-a72520e0.json
index.mobile-a72520e0.jsonl
embeddings.mobile-a72520e0.0.bin
```

Observed facts:

- 6,736 JSONL vector records
- 6,736 unique chunk IDs
- binary shard size: 2,990,784 bytes
- record size: 444 bytes
- 6,736 * 444 = 2,990,784 exactly
- every locator passed validation
- every record dimension is 384
- every offset is valid and aligned to the 444-byte stride
- all 6,736 CRC-32 checks passed

The metadata identifies:

```text
modelId: tooape/granite-embedding-97m-multilingual-r2-GBQ4-ONNX
revision: 54db88c5667bd79b4aea24ea6027a7ef45a7bbb5
chunkerVersion: 10
dim: 384
format: 3
deviceId: mobile-a72520e0
```

Each vector record is:

```text
[q:384 signed int8 bytes]
[s:8-byte little-endian float64]
[sign:48 packed sign-bit bytes]
[crc:4-byte little-endian CRC-32]
```

The vector is reconstructed as:

```text
storedVector[i] = q[i] * s
```

The sidecar JSONL is only a locator. Its record fields include:

```text
id, dim, shard, seq, off, mtime
```

The binary record contains no note path, title, chunk text, or metadata.

### What remains in Seek's IndexedDB

Seek's source documents the IndexedDB stores as:

```text
chunks      chunk ID -> chunk text and metadata
embeddings  chunk ID -> quantized vector { q, s }
binary      chunk ID -> packed sign-bit vector
files       note path -> chunk IDs
meta        index configuration
```

The required join is:

```text
files.note_path
   -> files.chunk_ids
   -> chunks
   -> embeddings / binary
```

The current three-file `Seek Index/` export contains the vector side, but not the chunk/file mapping side. Therefore an external MCP process cannot turn a vector hit into a useful note result from those files alone. The chunk ID is a path-salted cyrb53 hash and is not reversible.

The current sample's sidecar is therefore valid but incomplete for external retrieval.

### Graphthulhu investigation

The repository inspected was:

```text
https://github.com/skridlevsky/graphthulhu
```

It is an archived Go MCP server. Its Obsidian backend:

- reads `.md` files directly from a configured vault path
- parses frontmatter, headings, blocks, tags, and wikilinks
- builds an in-memory graph
- builds a simple inverted full-text search index
- watches the filesystem for changes
- provides MCP stdio and optional HTTP transports
- includes path-confinement logic

It does not:

- access IndexedDB
- access Seek's database
- read Seek sidecars
- load embeddings
- perform vector search

Graphthulhu is useful as a reference for MCP server setup, tool registration, transports, vault path safety, and backend organization. It is archived, so it should be treated as a reference implementation rather than a dependency. Its full-text search is not the semantic search engine required here.

### Architectural decision

Modify Seek's source so that it intentionally exports the missing document/mapping data while it already has access to IndexedDB. Then build the external MCP server against that complete export.

The chosen data flow is:

```text
Seek inside Obsidian
   -> reads its existing IndexedDB stores
   -> writes a complete semantic export into the vault
   -> Git syncs the agent vault copy
   -> external MCP server reads the export
   -> PicoClaw receives semantic retrieval results
```

This does copy chunk text and metadata, but it does not repeat embedding computation. It also avoids making the external MCP process depend forever on Seek's private IndexedDB schema.

The alternative live-bridge design remains possible:

```text
Obsidian-side bridge plugin
   -> reads Seek IndexedDB directly
   -> serves search/fetch operations
External MCP server
   -> communicates with bridge
PicoClaw
```

That design minimizes copying but introduces mobile IPC/HTTP complexity and tight coupling to the private database schema. It should be considered only if export size or sync latency becomes a real problem.

### Proposed complete export

Keep the existing vector sidecar format unchanged initially. Add a document layer beside it, for example:

```text
Seek Index/
  meta.<device>.json
  index.<device>.jsonl
  embeddings.<device>.<seq>.bin
  documents.<generation>.jsonl
  files.<generation>.json
```

A document record should contain at least:

```json
{
  "chunkId": "0190363da319fc",
  "notePath": "Projects/example.md",
  "title": "Example",
  "content": "The chunk text...",
  "chunkIndex": 0,
  "mtime": 1788404404143,
  "metadata": {}
}
```

Export metadata should include:

```json
{
  "schemaVersion": 1,
  "generation": "...",
  "modelId": "...",
  "revision": "...",
  "chunkerVersion": 10,
  "dim": 384,
  "sidecarFormat": 3,
  "chunkCount": 6736
}
```

The generation ID prevents mixing vectors from one build with text/mappings from another. The metadata/commit marker should be written last.

Export writing should be atomic:

1. create temporary export files or a temporary directory
2. read the existing IndexStore data
3. write all document and mapping records
4. validate counts and joins
5. write the metadata commit marker last
6. rename into place

Start with explicit full export after a completed full reindex. Do not export after every chunk update in the first version; that would create needless mobile and Git churn.

### Implementation plan

#### Phase 1: Seek export module

Work in the Seek source repository at `/workspaces/Obsidian-Seek`.

Use the existing `IndexStore` API rather than duplicating IndexedDB transaction code. Identify or add APIs for:

- listing all chunks
- reading chunk metadata
- reading chunk bodies
- reading file records
- reading quantized embeddings
- reading packed sign-bit vectors
- reading index metadata/configuration

The exporter must join the `files`, `chunks`, `embeddings`, and `binary` stores by `chunk_id`.

#### Phase 2: Seek export validation and lifecycle

Validate before publishing an export:

- chunk IDs are unique
- every vector has a corresponding document record
- every document has a note path and body
- every chunk maps to a valid note path
- dimensions match the active model
- vector/document counts are reported
- paths remain within the vault
- incomplete temporary exports are ignored or removed

Initially trigger the export through an explicit command or settings action. Add automatic export after successful full reindex only after the explicit path is reliable.

#### Phase 3: MCP server skeleton in this repository

The current `Obsidian-Seek-MCP` repository is documentation-only. Create the standalone MCP server here.

Graphthulhu suggests a Go implementation because it already demonstrates the official Go MCP SDK, stdio transport, optional HTTP transport, and backend abstractions. TypeScript is also viable because Seek's binary format is already implemented in TypeScript. Choose one deliberately before scaffolding; do not mix runtimes without a concrete reason.

The server needs:

```text
metadata loader
JSONL locator loader
document manifest loader
binary shard reader
CRC validator
record decoder
cosine scorer
result grouper
MCP tool handlers
```

#### Phase 4: Initial search implementation

Implement a full scan first:

```text
query embedding
   -> decode each stored int8 vector
   -> cosine similarity
   -> top-k chunks
   -> group/deduplicate by note
   -> return note path, score, title, chunk text
```

The current 6,736-vector corpus is small enough for a straightforward scan. Optimize only after correctness is established.

The packed sign-bit tier can later provide candidate generation:

```text
sign-bit scan
   -> top-N candidates
   -> int8 dequantized cosine rerank
   -> note/chunk grouping
```

#### Phase 5: Query embedding

The stored document vectors cannot embed a new query. Add a separate query-embedding component that either:

- runs the same Granite model locally
- calls a configured local embedding helper
- accepts a precomputed vector for testing/internal use

The model, revision, preprocessing, normalization, and dimension must match Seek. First make the search engine accept an injected 384-dimensional query vector so the index/search layer can be tested independently of ONNX/runtime integration.

#### Phase 6: Initial MCP tools

Implement read-only tools:

```text
semantic_search
fetch_note
fetch_chunk
index_status
```

`semantic_search` should support query text, top-k, optional path filters, and result-size limits. It should return note path, title, chunk ID, score, and content.

`fetch_note` and all path-based operations must enforce vault-root confinement. No arbitrary absolute paths, writes, Git commands, or mutation tools in v1.

#### Phase 7: Testing and real-data verification

Add synthetic fixtures so tests do not depend on `/workspaces/system-vault`.

Required tests:

- metadata/version rejection
- JSONL shape and dimension validation
- multi-shard offset resolution
- binary record decoding
- signed int8 handling
- CRC failure rejection
- cosine ranking against known vectors
- vector-to-document joins
- missing mapping behavior
- duplicate ID detection
- path traversal rejection
- generation mismatch rejection
- complete load of the real 6,736-record export

Only after this works should the server be connected to PicoClaw.

### First coding slice

The first implementation work should be narrow and executable:

1. Inspect the exact `IndexStore` methods and database name/schema in Seek.
2. Add an exporter that reads existing IndexedDB data.
3. Export one complete generation containing chunk text and note mappings.
4. Add fake-IndexedDB tests for the exporter.
5. Run the exporter against the real system vault.
6. Create the MCP server skeleton in this repository.
7. Implement sidecar/document loading and `index_status`.
8. Implement semantic search with an injected query vector.

The first discriminating success check is:

```text
every one of the 6,736 vector IDs resolves to a chunk body and note path
```

Until that passes, the external MCP server cannot provide useful semantic retrieval regardless of how good its MCP protocol implementation is.

### Known risks and constraints

- Seek's IndexedDB schema is private and may change.
- Exporting on every update may create excessive mobile storage/Git churn.
- The current sidecar metadata has one device ID; multi-device conflict and freshest-record rules need to be preserved if exports combine devices.
- The exact query embedding runtime may be the hardest deployment issue on Android/Termux.
- Seek's chunking, preprocessing, normalization, and model revision must match for retrieval quality.
- The sign-bit tier is derived from the original fp32 vector and cannot reconstruct that original vector.
- The MCP server should remain read-only because the agent vault is intentionally separate from the human source-of-truth vault.
- Graphthulhu is archived and should not be treated as a maintained dependency.

## Next-session directive: compatibility-first maintenance

The project is deliberately in a middle ground: the external MCP server must
understand Seek's persisted data, but it must run outside Obsidian in Node and
must expose MCP tools. The maintenance strategy is therefore compatibility
first, not independent reimplementation.

For every format-sensitive area, keep the MCP counterpart as close to Seek as
practical. Preserve the upstream file names, module boundaries, type names,
constants, variable names, function names, control flow, comments, and even
harmless unused helper functions when doing so reduces future diffs. The goal
is to make an upstream update a localized, mechanical comparison of matching
files rather than a reconstruction of behavior from scratch.

The code must still distinguish copied or closely adapted Seek blocks from new
code. Node filesystem adapters, MCP transport, tool handlers, document
manifests, and joins have no direct upstream equivalent and should remain at the
boundary. Do not force Obsidian UI or IndexedDB lifecycle code into the MCP
runtime merely to make the files look similar.

Attribution is mandatory for every copied or substantially adapted block. Keep
the upstream repository URL, exact source commit, original source path, and MIT
license visible in the file or its companion notice. Maintain the source map in
`UPSTREAM.md`. Do not describe an adapted block as byte-for-byte identical when
imports, runtime APIs, or filesystem behavior differ.

When Seek changes, use this update procedure:

1. Compare the pinned Seek commit with the new Seek version.
2. Inspect `quant.ts`, `sidecar.ts`, `binary.ts`, model metadata, relevant types,
   and IndexedDB schema/read APIs.
3. Port corresponding compatibility blocks while preserving upstream structure.
4. Update the exporter only where the upstream schema or lifecycle requires it.
5. Update `UPSTREAM.md`, attribution, fixtures, and format-version gates.
6. Run MCP build/tests, Seek typecheck/tests, and a real-export validation.

The ordered task list lives in `todo.md`. Its priority tags are `[critical]`,
`[important]`, and `[optional]`; complete earlier critical work before later
optimization work. The highest-value validation remains the complete join:
every native Seek vector ID must resolve to a valid document and note path.
